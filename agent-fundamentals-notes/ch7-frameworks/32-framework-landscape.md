# 32 · 用六大支柱理解任何 Agent 框架

> 章节：第七章 回到框架

## 生产中会遇到的问题

新框架出现时，官方文档给出的说明是「提供了完整的 Agent 开发能力」。这句话没有说明它在六大支柱上各做了什么选择，因此无法判断是否适合自己的项目。

## 底层机制

框架可以按作用层次分成四类。

| 层次 | 职责 | 代表形态 |
|------|------|----------|
| 模型调用层 | 统一各家接口、流式解析、重试 | 统一供应方接口的库 |
| 控制流层 | 循环、条件转移、状态、检查点 | 图结构框架 |
| 工具与能力层 | 工具注册、MCP 接入、检索 | 各类工具集合与检索组件 |
| 一体化层 | 循环、工具、界面、部署全部包含 | 各家 Agent SDK 与产品 |

按六大支柱逐项对照，任何框架的位置就清楚了。

| 支柱 | 需要确认的问题 |
|------|----------------|
| Agent Loop | 循环由框架控制还是由开发者控制，能否插入自定义终止条件 |
| Tool System | 工具定义格式、结果处理与截断是否可定制、并发策略 |
| Context Engineering | 每一轮请求由谁装配，能否打印完整请求，压缩策略在哪里 |
| Memory 与 RAG | 是否内置，存储形态是什么，能否替换 |
| Multi-Agent | 子智能体的上下文隔离方式，回传格式能否定制 |
| Harness | 权限、Hook、观测、部署是否提供，扩展点在哪里 |

## 实现要点

**模型调用层与控制流层分开选择。** 这两层解决的问题不同，来自不同项目是正常状态。

**确认请求是否可见。** 无法打印模型实际收到的完整请求的框架，在出现质量问题时几乎没有排查手段。

**确认更换模型供应方的代价。** 直接调用各家 SDK 的框架在更换供应方时需要改动请求构造与响应解析两处。

**确认状态持久化的形态。** 状态保存在框架内部结构里还是写在可读文件中，决定了排查问题与手工修复的难易程度。

**避免同时使用两套控制流。**

## pi 的做法

按六大支柱逐项核对 pi，它的选择如下。

| 支柱 | pi 的选择 | 可核对的证据 |
|------|-----------|--------------|
| Agent Loop | 自己实现线性双层循环，不用框架编排 | `pi-agent-core/dist/agent-loop.js` 的 `runLoop` |
| Tool System | 8 个内置工具，工具自带系统提示词贡献与渲染器，并发策略由工具声明 | `dist/core/tools/index.js`、`tools/read.js` 的 `executionMode` 与 `promptGuidelines` |
| Context Engineering | 系统提示词按段落组装并增量更新；请求可在 `before_payload` 处完整取得 | `dist/core/system-prompt.js` 的 `diffSystemPromptSections`、`harness/hooks.js` |
| Memory 与 RAG | 会话树作为短期记忆；长期记忆与检索由扩展提供 | `dist/core/session-manager.js`、`~/.pi/agent/memory/` |
| Multi-Agent | 子会话独立，上下文模式可选，写操作可放进独立工作树 | `pi-subagents/src/runs/`、`src/shared/pruned-fork.ts` |
| Harness | Hook 注册表、事件总线、遥测、会话持久化、信任判定、RPC 模式齐备 | `pi-agent-core/dist/harness/`、`dist/core/`、`dist/modes/rpc/` |

分层上，pi 把模型调用层单独做成一个包（`pi-ai`），因此更换供应方不影响循环。控制流层与外壳层合成一个包（`pi-agent-core`），因为它们的变化频率接近。应用层单独一个包（`pi-coding-agent`），因为它包含产品行为。编排与多智能体作为一个可选的扩展包（`pi-subagents`），不使用时不引入。

这套划分给出一个可复用的判断方式：把「与具体供应方有关」「与运行方式有关」「与产品行为有关」「与任务编排有关」四类内容放到不同的包里，任何一类发生变化时改动范围都是可预期的。

**不引入的部分也要记录。** pi 核心没有 MCP 客户端，没有向量检索，没有轮数上限的配置项。这些空缺是有意留下的：选择权交给扩展与运行方式。需要时由扩展补上，不需要时不付出复杂度与上下文成本。评估一个框架时，这类空缺与它提供的功能同样重要。

## 常见错误

第一个错误是按功能列表选择框架。功能数量与实际使用到的部分之间存在明显差距。

第二个错误是忽略请求可见性。上线之后出现问题无法定位。

第三个错误是把一体化方案的内部循环当作可以定制的部分。改动需要绕过框架机制，升级时全部失效。

第四个错误是同时接入多个控制流框架。行为不一致。

第五个错误是不记录框架的空缺。空缺在需求出现时才被发现，此时改动代价最高。

## 自检问题

1. 你当前使用的框架覆盖哪几根支柱？
2. 你能打印它实际发出的完整请求吗？
3. 更换模型供应方需要改动哪些文件？
4. 你使用的框架有哪些明确的空缺，由什么补上？
