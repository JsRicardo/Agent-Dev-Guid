# 7 · Agent Loop 的三个保险丝

> 章节：第二章 Agent Loop

## 生产中会遇到的问题

无人值守运行的 Agent 出现过几类典型故障：对着同一个报错反复调用同一个命令，几十轮之后额度耗尽；把同一个文件读取十几次，每一轮都消耗完整上下文；任务已经完成但模型继续探索，最终把简单任务扩展成大范围改动。

这三类故障的成因都在程序侧：缺少终止条件。模型在其中只是按给定内容作答。

## 底层机制

**保险丝一：轮数与时间上限。** 按任务类型设置不同的最大轮数。单次问答需要三轮以内，代码修改任务需要二十到五十轮。达到上限时进入收尾流程：要求模型基于当前已有信息给出结论，说明哪些部分没有完成。

**保险丝二：重复动作检测。** 对每一次工具调用计算指纹，指纹由工具名称与规范化之后的参数组成。维护最近若干次调用的指纹列表，出现连续重复时介入。

| 连续重复次数 | 处理方式 |
|--------------|----------|
| 2 | 在工具结果中附加提示，说明上一次调用的结果 |
| 3 | 注入一条使用者消息，要求模型改变策略 |
| 5 | 终止循环，返回当前进展 |

**保险丝三：Token 预算。** 累计输入与输出 Token，设定单任务上限。预算耗尽时与轮数上限处理方式相同。预算比轮数更准确，因为一轮请求的成本可能相差几十倍，取决于工具结果的长度。

还有一类检测值得加入：无进展判定。连续若干轮没有产生新的信息，例如工具结果与之前相同、模型输出的内容与上一轮高度接近，同样应当触发收尾。

## 实现要点

```typescript
type FuseState = {
  step: number;
  fingerprints: string[];
  totalInputTokens: number;
  totalOutputTokens: number;
};

function checkFuses(state: FuseState, limits: Limits): FuseAction {
  if (state.step >= limits.maxSteps) return { type: 'finalize', reason: '轮数上限' };
  if (state.totalInputTokens + state.totalOutputTokens >= limits.maxTokens)
    return { type: 'finalize', reason: 'Token 预算' };

  const tail = state.fingerprints.slice(-2);
  if (tail.length === 2 && tail[0] === tail[1])
    return { type: 'nudge', message: '上一次调用没有解决问题，请换一种方式' };

  return { type: 'continue' };
}
```

指纹计算需要规范化参数。同一个路径写成相对路径与绝对路径、参数顺序不同、空白字符不同，都会导致指纹不一致，检测完全失去作用。规范化方式是按固定字段顺序序列化，并统一路径形式。

收尾流程需要独立实现，不能复用正常回答路径。收尾时应当限制工具使用，只允许输出文本结论，避免收尾本身继续消耗预算。

## pi 的做法

pi 在主循环里没有轮数上限，也没有重复动作指纹检测。它用另外四种机制达到相近的效果，每一种都可以核对。

**机制一：上下文窗口本身就是上限。** 循环无法无限进行，因为每一轮的工具结果都会留在请求里，请求长度会持续增长。增长到窗口阈值时压缩介入，压缩按 `keepRecentTokens` 保留最近内容，早期内容被摘要替换。任务无限重复时，摘要会反复出现同样的结论，模型在摘要里看到自己已经做过的事情。

**机制二：截断与工具结果的长度约束。** `dist/core/tools/truncate.js` 对工具结果设置两个上限，谁先命中按谁处理：2000 行与 50KB。读取类工具保留开头，命令类工具保留结尾，`grep` 的每一行再截到 500 字符。单个工具结果无法把预算一次性占满。

**机制三：中止与人在环。** `AbortSignal` 贯穿请求、工具批次、并发批次内的每一项。使用者在界面上中止之后，循环在下一个检查点停止。steering 消息允许使用者在一轮进行中插入修正，不需要等到整轮结束。

**机制四：异常形态的分类处理。** `stopReason` 取 `error` 或 `aborted` 时直接结束；取 `length` 时不执行工具调用，把整批调用标记为失败并要求模型重新发起。这三种情况之外的增广型故障交给重试层。

在子智能体侧，pi 提供了显式的预算机制。`pi-subagents` 的工具参数里有 `toolBudget`（软上限与硬上限，达到硬上限之后按白名单屏蔽读取类工具迫使子智能体收尾）、`usageBudget`（Token 与金额上限）、`timeoutMs`、`maxSubagentSpawnsPerRun`。父级预算通过 `spawn-budget` 与 `run-fanout-budget` 向子级划拨，避免嵌套两层之后总额度被放大数倍。

## 常见错误

第一个错误是只限制轮数不限制 Token。一轮请求携带超长工具结果时，成本失控发生在单轮之内。

第二个错误是重复检测只看工具名称。同一个工具用不同参数反复调用同样是无效行为。

第三个错误是达到上限后直接抛出异常。使用者看到的是错误提示，已经完成的工作全部丢失。

第四个错误是认为有了压缩就不需要终止条件。压缩限制的是长度，不限制轮数，慢速空转依然会消耗成本。

第五个错误是子智能体各自使用独立预算。嵌套三层之后总消耗可能达到预期的十倍。

## 自检问题

1. 你的循环终止条件有哪些，各自的触发频率是多少？
2. 重复动作检测覆盖了参数差异吗，路径形式统一了吗？
3. 收尾流程与正常回答路径是分开实现的吗？
4. 子任务的额度是从父任务划拨的，还是各自独立的？
