# 28 · Hook 与可观测性

> 章节：第六章 Harness 进阶

## 生产中会遇到的问题

Agent 运行过程中出现问题，能拿到的信息只有最终的输出结果。中间调用了哪些工具、参数是什么、执行了多久、消耗多少 Token，全部不清楚。判断问题的原因只能靠推测。

## 底层机制

Hook 是执行流程中的扩展点。按位置分为四类：

| 类型 | 触发时机 | 典型用途 |
|------|----------|----------|
| 工具前置 | 工具执行之前 | 参数校验、权限判定、参数补充 |
| 工具后置 | 工具执行之后 | 结果格式化、截断、审计 |
| 消息级 | 每次请求前后 | 上下文注入、缓存统计 |
| 会话级 | 会话开始与结束 | 环境准备、记录归档 |

可观测性解决的是记录问题。需要记录的事件包括请求、回应、工具调用、工具结果、权限判定、错误，每一类都带时间与用量。

## 实现要点

**记录完整请求内容。** 出问题时唯一有效的排查方式是查看模型实际收到的内容。

**记录工具参数与结果摘要。** 参数需要完整记录，结果可以记录长度与前若干字符。

**耗时按阶段记录。** 首字延迟、生成耗时、工具执行耗时、总耗时分开统计。

**脱敏。** 请求内容可能包含密钥、令牌、个人数据。记录之前需要过一遍过滤。

**可回放。** 记录内容应当支持重新构造请求。

## pi 的做法

Hook 与可观测性在 pi 里是两个独立组件，各自有明确职责。

**Hook 注册表。** `pi-agent-core/dist/harness/hooks.js` 的 `HookRegistry` 提供 `on(name, handler, options)`，返回取消订阅的函数。已经注册的 Hook 按注册顺序调用，聚合方式按扩展点的语义决定。

| 扩展点 | 聚合方式 | 能改动什么 |
|--------|----------|------------|
| `before_run` | 全部调用 | 追加初始消息 |
| `before_drive` | 全部调用，失败即关闭 | 无返回值 |
| `before_run_end` | 全部调用 | 提供后续消息 |
| `transform_context` | 依次串联 | 消息序列与系统提示词 |
| `before_request` | 依次串联 | 流参数 |
| `before_payload` | 依次串联 | 即将发出的完整请求体 |
| `after_response` | 依次串联 | 助手消息 |
| `before_tool` | 首个返回阻止者生效 | 参数、阻止原因 |
| `after_tool` | 依次串联 | 工具结果 |
| `before_compaction` | 首个结构化返回值生效 | 压缩相关 |
| `before_navigation` | 首个结构化返回值生效 | 分支摘要相关 |

三个可核对的设计点：

- **失败隔离。** 单个 Hook 抛出异常不会中断流程。异常被归一化之后通过 `reportError` 上报，`events.js` 会额外发出一条 `handler_error` 事件。这样某个扩展出错时，其余扩展仍然正常工作。
- **注册顺序即调用顺序。** 需要「先做校验再做加工」时靠注册顺序表达，不需要额外的优先级字段。
- **`before_payload` 是可观测性的关键位置。** 它拿到的 `payload` 是即将发出的请求体，记录这里的内容就得到了完整的请求现场，也是回放的基础。

**事件总线。** `harness/events.js` 的 `HarnessEventBus` 提供 `on(type, listener)` 按类型订阅，`emit` 与 `emitBatch` 投递。投递前对事件做结构化复制，避免监听方修改事件影响其他监听方。`watch` 提供带快照的订阅：先记录当前状态，再从快照边界之后接收新事件，用于需要「从此刻开始观察」的组件。

事件总线与 Hook 注册表的差别在于是否影响执行：Hook 的返回值会改变流程，事件只是通知。两者分开之后，观测代码不会意外改变行为。

**遥测。** `harness/telemetry.js` 提供跨度记录，Hook 调用与工具调用各自开跨度。同一批次的工具调用可以按批次与单项两级观察。

**会话文件即完整记录。** 会话以 JSONL 保存，条目类型包括消息、模型切换、思考等级切换、用量、压缩、分支摘要、上下文编辑。用量条目记录供应方、模型与四项 Token 计数，`kind` 字段区分用途。要还原一次运行中发生了什么，读会话文件即可，不需要额外的日志系统。

**缓存误失的对外提示。** `cache-stats.js` 把每一轮的误失量与金额算出来之后，可以按条显示在对应助手消息上。这一处把成本问题变成可见信息：使用者看到「这一轮缓存失效，多花了多少」之后，才会去检查是什么让前缀发生了变化。

**子智能体侧的记录。** `pi-subagents` 为每次运行保存 `status.json`、`events.jsonl` 与日志，另有 `run-history.jsonl` 汇总历史运行。查看用 `status` 与 `debug.run`，两个视图分别面向「现在什么状态」与「这一路怎么走到这里」。

## 常见错误

第一个错误是只记录结果不记录请求。问题的原因通常出现在输入上。

第二个错误是工具结果全文记录。日志迅速膨胀，实际很少查看。

第三个错误是耗时统计只记录总时长。无法判断是模型慢还是工具慢。

第四个错误是 Hook 出错时中断整个流程。单个扩展的问题影响到全部工作。

第五个错误是观测代码通过修改参数来记录。观测应当走事件通道，不应当改变执行。

第六个错误是不脱敏。密钥进入日志文件。

## 自检问题

1. 你能查看最近一次执行中模型收到的完整请求吗？
2. 你的 Hook 出错时会中断整个流程吗？
3. 你的记录里有首字延迟这一项吗？
4. 观测代码会改变执行流程吗？
