# 3 · 做 Agent 开发必须了解的大模型机制

> 章节：第一章 认知校准

## 生产中会遇到的问题

同一段提示词在 A 模型上表现良好，换到 B 模型之后工具调用开始出错；工具从 10 个增加到 30 个之后，模型选错工具的比例上升；上下文填充到八成长度之后，模型开始忽略开头的指令。这些现象都能在模型机制里找到解释。

## 底层机制

**分词与 Token 计数。** 模型处理的最小单位是 Token。英文大约每四个字符一个 Token，中文大约每个字一到两个 Token。这带来两个直接后果：中文提示词的成本高于同等信息量的英文；工具定义的 JSON Schema 也会被计入 Token。工具集合膨胀的成本不只是模型的选择负担，还有每一轮请求都要重复支付的固定开销。

**注意力与上下文长度。** 自注意力计算量随序列长度呈平方增长。上下文从 10 万 Token 增加到 20 万 Token，计算量增加到四倍左右。这解释了长上下文的价格结构。

**位置效应。** 序列中间位置的信息被利用的比例低于开头与结尾。把关键指令放在系统提示词开头仍然有效，把关键指令放在一段长工具结果之后则容易被忽略。

**采样与随机性。** temperature 与 top_p 控制输出的随机程度。工具调用需要稳定的参数结构，温度过高会让参数出现格式错误；创意写作需要多样性，温度过低会让输出重复。同一个 Agent 程序里两类任务往往并存，因此采样参数需要在单次调用层面设置。

**约束解码与结构化输出。** 结构化输出的可靠实现方式是在解码阶段限制可选 Token，使输出必然符合给定的 JSON Schema。这种方式保证语法正确，但不保证语义正确：枚举值可以合规，含义仍然可能选错。

**KV Cache。** 解码时每一层对历史 Token 的键值计算结果可以复用。这正是流式输出能够成立的原因。提示词缓存把这份复用扩展到跨请求的层面，要求前缀完全一致，因此系统提示词里插入一个动态时间戳就会让缓存全部失效。

**推理模型的思考 Token。** 带推理能力的模型在给出答案之前会生成一段思考内容。这段内容计入输出 Token，需要付费，也会影响首字延迟。对 Agent 来说，思考内容在处理简单工具调用时是浪费，在处理复杂规划时有价值。

**知识截止与幻觉。** 训练数据的截止时间决定了模型对近期信息的缺失。模型在缺失信息时的表现是继续生成看似合理的内容，语气与正确内容没有区别。工程上的应对方式是让所有需要事实的地方都走工具或检索，并且让工具返回的内容带上来源。

## 实现要点

模型选择的判断依据是任务类型：

| 任务 | 关注点 |
|------|--------|
| 工具选择与参数生成 | 工具调用准确率、结构化输出稳定性 |
| 长文档理解 | 上下文窗口、位置效应敏感度、缓存支持 |
| 规划与分解 | 推理能力、思考 Token 成本 |
| 内容生成 | 采样参数、风格稳定性 |

前缀稳定性的实现方式是把所有动态内容从系统提示词中移出。时间、使用者标识、会话标识放在第一条用户消息里，系统提示词保持逐字节一致。

Token 预算的估算应当在请求发送之前完成。常见做法是按字符数简单折算，中文按一点五倍字符数、英文按零点三倍字符数，再加上工具定义的固定开销。

## pi 的做法

`pi-ai` 把上面这些机制都做成了模型元数据与用量字段，程序按字段判断，不按模型名称判断。

- 模型对象上带 `contextWindow`、`inputLimits`（各类输入的上限与图片缩放参数）、`promptCache`（不同保留策略对应的缓存存活秒数）。
- `reasoning` 与思考等级是请求参数，可以在单次调用层面设置，pi 在压缩、缓存续期这类内部调用里分别使用不同的取值。
- 用量结构固定为 `input`、`output`、`cacheRead`、`cacheWrite` 四项加 `reasoning`，另有 `totalTokens` 与成本字段。缓存读写单独计价，所以必须分开统计。
- Token 估算在 `dist/core/compaction/compaction.js` 里用字符数除以四的方式完成，注释里明确写了这个方法会高估，属于有意的保守估计。
- 结构化输出通过工具定义上的 `constrainedSampling: { type: "json_schema", strict: "prefer" }` 表达，`strict` 取 `prefer` 表示供应方支持时启用约束解码，不支持时退回普通模式。
- `pi-ai/dist/utils/overflow.js` 里维护了一份按供应方整理的上下文溢出错误文本对照表，因为各家报错措辞不同，靠状态码无法区分。

## 常见错误

第一个错误是按字符数估算 Token，导致上下文超限。中文场景下误差可以翻倍。

第二个错误是在系统提示词里拼接时间戳。缓存失效之后成本成倍上升。

第三个错误是对简单工具调用使用推理模型。首字延迟从一秒变成十几秒，成本增加数倍。

第四个错误是把结构化输出的合规当作语义正确。参数符合 Schema 不代表参数是模型真正想表达的取值。

第五个错误是让模型回答需要事实核查的问题。任何涉及具体数据、日期、版本的内容都应当来自工具。

## 自检问题

1. 你的系统提示词里有没有每次请求都会变化的字段？
2. 你的用量统计里有 `cacheRead` 与 `cacheWrite` 两项吗？
3. 你的程序在什么任务上使用了推理模型，延迟如何？
4. 你的提示词里，关键约束位于整个请求的哪个位置？
