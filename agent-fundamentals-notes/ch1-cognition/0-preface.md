# 0 · 从用法到判断力

> 章节：第一章 认知校准

## 生产中会遇到的问题

学 Agent 的人常常卡在同一批问题上。教程看了一堆，换一个产品又不会做了；跟着某个项目抄了一遍代码，自己设计工具集合时仍然没有判断依据；面试时能说出名词，被追问「为什么这里要这样设计」就答不上来。

出现这种状态的原因在于，多数内容只讲用法。用法是某个产品和某个版本的具体选择，产品的结构一变，用法的价值就消失。而 Agent 的工程结构在过去两年里变化频繁：从固定流程的 Chain，到单一循环，到带动态工具集的循环，到带子智能体的循环。任何跟着用法学的路径都会持续失效。

这份讲义选择的位置是决策层：真实产品为什么这样选，替代选择会在什么条件下更好。学习目标是能够独立回答设计问题。

## 底层机制

一个 Agent 程序可以看作四个层次的叠加。

| 层次 | 内容 | 变化速度 |
|------|------|----------|
| 模型能力 | 上下文窗口、工具调用能力、推理能力 | 每季度 |
| 工程结构 | 循环、工具系统、上下文装配 | 每半年 |
| 运行时外壳 | 权限、观测、调度、部署 | 每一年 |
| 具体框架 | LangChain、LangGraph、Vercel AI SDK | 每几个月 |

学习投入应当与变化速度成反比。模型能力部分只需要理解机制，不需要记忆具体参数。工程结构部分需要动手实现一遍，因为它决定了程序的形状。运行时外壳部分需要理解设计动机，因为线上事故大多出在这一层。具体框架部分只需要知道它解决的是哪一层的什么问题。

另一种常见的认识误区是把 Agent 等同于提示词工程。提示词工程解决的是单次调用的输出质量。Agent 程序处理的是多轮循环中的状态累积、工具结果的取舍、失败之后的恢复，这些内容无法通过打磨一段提示词解决。

## 实现要点

建立判断力的方式是对照实现。同一件事在三个真实产品里的做法各不相同，把三处实现摆在一起，差异会自然显出设计的约束条件。

例如「工具执行结果如何反馈给模型」这个问题，三种做法对应三种约束：

- 把结果截断到固定长度，超出部分提示模型改用分页读取，对应上下文预算充足但输出长度不可控的场景；
- 把结果完整放回，依赖模型的注意力完成取舍，对应上下文预算充裕、信息损失不可接受的场景；
- 先做一次局部压缩再放回，对应上下文预算紧张、只需要结论的场景。

理解了约束，才能在自己的场景里做出选择。学习的检查点可以设为：读完之后能否用一段话讲清某个设计解决了什么问题，以及如果不这样做，会在什么场景下出事。

## pi 的做法

pi 的包结构本身就是上面那套分层的一个实例，可以直接当作对照对象。

```
@earendil-works/pi-ai           模型调用层：统一各家接口、流式事件、重试分类、用量与成本
@earendil-works/pi-agent-core   循环与外壳：agent-loop.js、harness/（hooks、events、telemetry、session）
@earendil-works/pi-coding-agent 应用层：会话、工具、压缩、技能、系统提示词、信任判定、界面模式
pi-subagents                    编排层：子会话、worktree 隔离、预算、工作流
```

这份讲义后续每一讲都会指向其中一个位置。变化速度的差别在这套包里也看得到：`pi-ai` 里的供应方适配改动频繁，`agent-loop.js` 的循环结构改动很少，`hooks.js` 里的扩展点名称一旦发布就长期保持稳定。

## 常见错误

第一个错误是按照产品追新。Manus 出来学 Manus，OpenClaw 出来学 OpenClaw，每个产品都学一遍表层用法，知识之间无法互相支撑。

第二个错误是把实现细节当作原理背下来。上下文窗口是 200K 这类数字，半年后就会变化，记住它没有任何收益。

第三个错误是只读不写。Agent 的多数问题在纸面上看不出来，比如流式渲染与工具调用的顺序冲突，只有写出来跑一遍才会暴露。

第四个错误是把框架当作学习对象。框架的价值在于减少重复代码，学习框架的收益上限取决于对底层机制的掌握程度。
