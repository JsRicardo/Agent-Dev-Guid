# 8 · Function Calling 与 Structured Output

> 章节：第三章 Tool System

## 生产中会遇到的问题

初学时的常见困惑是模型如何执行本地函数。实际上模型没有能力执行任何代码，它能做的只是生成一段符合给定结构的内容，程序读取这段内容之后自己去调用函数。

## 底层机制

工具调用的训练过程是在后训练阶段完成的。训练数据中包含大量「给定工具定义与对话历史，输出工具调用内容」的样本。模型学到的映射是：观察工具名称与描述，判断当前任务是否需要工具，需要时选择其中一个并按参数结构生成取值。

这套训练带来几个直接结果：

- 工具名称与描述参与选择过程，写法影响准确率；
- 参数取值来自描述中的说明与对话中的历史，缺信息时模型会猜测；
- 没有合适的工具时，模型仍然可能选择一个相近的工具；
- 同时给出多个工具时，选择准确率随数量下降。

结构化输出是同一机制的另一形态。区别在于工具调用输出的是调用内容，结构化输出直接约束最终回答的结构。两者的实现都依赖约束解码：在每一个生成位置屏蔽不符合结构的 Token。

## 实现要点

工具描述承担的工作比多数人预期的多。以下三件事都会影响选择准确率。

**名称使用动词开头的具体短语。** `searchCode` 与 `search` 相比，后者在前者存在时会被大量误选。

**描述说明使用时机。** 描述里写清「什么情况下应该使用」比写清「这个工具做什么」更有价值。

**参数取值尽量使用枚举。** 自由文本参数会让模型生成意料之外的取值。

结构化输出使用在需要程序解析模型输出结果的场景，例如模型生成的清单、分类结果、字段抽取。校验失败时应当把错误信息交回模型重新生成，重试次数需要限制。

## pi 的做法

`dist/core/tools/read.js` 的工具定义把上面几件事同时做完，可以逐项对照。

```typescript
const readSchema = Type.Object({
  path: Type.String({ description: "Path to the file to read (relative or absolute)" }),
  offset: Type.Optional(Type.Number({ description: "Line number to start reading from (1-indexed)" })),
  limit: Type.Optional(Type.Number({ description: "Maximum number of lines to read" })),
});

export const readToolSystemPromptContribution = {
  snippet: "Read file contents",
  guidelines: ["Use read to examine files instead of cat or sed."],
};
```

需要核对的结构：

- **类型定义与描述放在一起。** 参数用 TypeBox 描述，每个字段自带 `description`。参数名与描述在同一处，改动时不会遗漏。
- **描述里写明后果与替代路径。** `read` 的描述明确写出「输出被截断到 2000 行或 50KB，谁先命中按谁处理；处理大文件时使用 offset 与 limit；需要完整文件时用 offset 继续读取」。模型据此知道大文件该怎么做，不需要重新探索。
- **系统提示词贡献分两部分。** `snippet` 供系统提示词的 `tools` 段落使用，`guidelines` 供 `rules` 段落使用。工具可以在注册时把自己的使用规则送进系统提示词，不需要集中维护一份工具说明。
- **约束采样显式声明。** 定义里带 `constrainedSampling: { type: "json_schema", strict: "prefer" }`。`prefer` 表示供应方支持时启用严格的结构约束，不支持时退回普通模式，程序不必按模型分支处理。
- **工具自带渲染器。** 定义里引用 `readRenderers`，界面按工具类型渲染结果，与模型看到的文本内容分开维护。

`promptSnippet` 与 `promptGuidelines` 这套机制在 `dist/core/system-prompt.js` 的 `buildRules` 里被消费：遍历当前选中的工具，把每个工具的规则去重后合成 `rules` 段落。工具的规则跟着工具走，工具被移除时规则也随之消失。

## 常见错误

第一个错误是把工具描述写成函数文档。文档描述实现，工具描述面向模型判断，需要包含使用时机与边界。

第二个错误是同时暴露功能相近的工具。模型在两者之间的选择接近随机，应当在程序层面合并，把差异做成参数。

第三个错误是把参数设计成嵌套结构。嵌套层级越多，模型生成的出错概率越高，扁平的参数结构更稳定。

第四个错误是依赖结构化输出保证语义正确。结构合规只保证能被解析，字段取值是否合理需要单独校验。

第五个错误是把工具的使用规则集中写在系统提示词里。规则与工具分开维护之后，删除工具时容易漏掉对应的规则。

## 自检问题

1. 你的工具名称能让模型在只看名称时完成初步判断吗？
2. 每个工具的描述里有没有写清使用时机与不该使用的场景？
3. 你的参数里有多少个自由文本字段，能否改成枚举？
4. 你新增工具时需要改动几个文件？
