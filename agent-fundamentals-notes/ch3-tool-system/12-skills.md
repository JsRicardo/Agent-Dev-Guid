# 12 · Skills 与知识分发

> 章节：第三章 Tool System

## 生产中会遇到的问题

工具解决了「能做什么」的问题，没有解决「怎么做」的问题。某个任务的执行流程需要二十个步骤，涉及若干约定与检查点，这部分知识如果写进系统提示词，会在每次请求中永久占用上下文；如果不写，每次执行时都要重新说明。

Skills 提供的处理方式是把这些知识做成按需加载的文件单元。

## 底层机制

一个 Skill 是一个目录，入口文件包含元数据与正文，正文里可以引用目录内的其他文件与脚本。

元数据部分包含名称与说明。名称与说明是唯一始终参与请求的部分，正文只在 Skill 被触发之后才加载。这个特性决定了说明文字的写法与整个机制的运行效果。

加载分为三个阶段：

| 阶段 | 加载内容 | 占用 |
|------|----------|------|
| 阶段一 | 名称、说明、位置 | 每次请求 |
| 阶段二 | 入口文件正文 | 触发之后 |
| 阶段三 | 引用的文件与脚本 | 需要时单独读取 |

## 实现要点

**说明文字写触发条件。** 说明文字的作用是让模型判断「当前任务是否属于这个 Skill 的处理范围」。因此描述里应当包含使用场景与关键词。

**确定性部分写成脚本。** Skill 正文里涉及固定步骤的部分，应当写成可执行脚本，由正文说明调用方式。

**正文控制长度。** 正文过长会挤占上下文，同时降低模型遵循的程度。

**与工具的分工。** 工具提供执行能力，Skill 提供执行流程。把流程写进工具实现里会让工具难以复用。

**与 MCP 的分工。** MCP 解决跨产品的工具复用，Skill 解决跨产品的流程复用。

## pi 的做法

`dist/core/skills.js` 与 `docs/skills.md` 一起定义了 Skill 的完整生命周期，可以按五个问题核对。

**发现。** 从 `~/.pi/agent/skills` 与项目 `.pi/skills` 递归扫描，同时支持 `~/.agents/skills` 与 `.agents/skills` 这两个通用位置。发现规则是：目录里有 `SKILL.md` 就把它当作 Skill 根目录，不再向下递归；否则读取根目录下的直接 `.md` 文件，并继续向子目录递归。`.gitignore`、`.ignore`、`.fdignore` 三类忽略文件生效，`node_modules` 与点号开头的目录跳过。

**校验。** 名称长度上限 64 字符，只允许小写字母、数字、连字符，不允许首尾连字符与连续连字符；说明长度上限 1024 字符。名称与说明存在问题产生警告但不阻止加载；说明缺失时该 Skill 不被加载。名称冲突时保留先发现的那一个并产生冲突诊断。符号链接会解析到真实路径用于去重，同一个文件通过链接出现两次时只加载一次。

**注入系统提示词。** `formatSkillsForPrompt` 生成一段带标签的清单：

```markdown
<available_skills>
  <skill>
    <name>feishu-send-message</name>
    <description>用飞书机器人身份给指定用户发 1:1 私信……</description>
    <location>/Users/.../skills/feishu-send-message/SKILL.md</location>
  </skill>
</available_skills>
```

清单里包含位置字段，模型据此能直接读取入口文件，不需要猜测路径。同时注入的还有一句路径解析规则：Skill 文件里出现的相对路径相对于 `SKILL.md` 所在目录解析。缺少这句话时模型会把相对路径按工作目录解析。

`disable-model-invocation: true` 的 Skill 会从清单里排除，只能通过 `/skill:name` 显式调用。这是给「不希望模型自行触发」的 Skill 准备的位置。

**加载与段落更新。** 清单只出现在系统提示词的 `skills` 段落。Skill 被读取之后，正文进入会话历史；若因为新 Skill 出现导致清单变化，只有 `skills` 段落被重新写入，其他段落保持原样，提示词缓存不受影响。

**信任门禁。** 项目级 Skill 属于需要项目信任的资源。`dist/core/trust-manager.js` 的清单里列出了 `.pi/skills` 与项目 `.agents/skills`，未授予信任时这些目录不会被加载。使用者级 `~/.agents/skills` 始终视为已信任。

## 常见错误

第一个错误是说明文字只写功能。触发率低，Skill 存在但用不上。

第二个错误是把 Skill 写成文档。正文里全是背景介绍，缺少可执行步骤。

第三个错误是把所有细节放进正文。加载之后占用大量上下文，其中大部分内容本次任务用不到。

第四个错误是相对路径按工作目录解析。Skill 引用的脚本找不到，或者引用到了同名的其他项目文件。

第五个错误是 Skill 数量增长之后不整理。长期未触发的 Skill 应当删除，清单的累计开销与判断干扰都是实际成本。

## 自检问题

1. 你有哪些 Skill 从未被触发过？
2. 每个 Skill 的说明文字包含使用场景吗？
3. 你的 Skill 正文里引用的相对路径能解析到正确位置吗？
4. 哪些步骤在你的 Skill 里每次都由模型重新生成，能否改成脚本？
