# 26 · Agent Swarm 协作

> 章节：第五章 Multi-Agent

## 生产中会遇到的问题

单个 Agent 完成的任务在质量上存在波动：同一份需求两次实现的结果差别很大。引入第二个 Agent 做独立审查可以缩小波动，但协调逻辑写起来比单个 Agent 复杂得多：审查意见如何回传、返工次数如何限制、两个 Agent 同时修改同一份代码如何处理。

## 底层机制

协作形态有三种，各自适用于不同场景。

| 形态 | 结构 | 适用场景 |
|------|------|----------|
| 并行分工 | 多个 Agent 处理相互独立的子任务，结果汇总 | 子任务之间无依赖 |
| 流水线 | 前一个 Agent 的输出作为后一个的输入 | 阶段划分明确 |
| 交叉审查 | 一方产出一方验证，意见回传后继续 | 质量要求高 |

交叉审查是三种形态里协调逻辑最复杂的一种，因为它包含循环。

## 实现要点

**以任务目录作为协调媒介。** 每个任务有一个目录，存放任务说明、产出物、审查意见、轮次记录。

```
tasks/{task-id}/
  TASK.md          任务说明
  output/          产出物
  review/          审查意见
  rounds.json      轮次记录
```

**轮次上限。** 交叉审查必须设置最大轮次，达到上限之后交给使用者判断。

**返工指令需要结构化。** 审查意见按条目组织，每条包含位置、问题、期望结果。

**独立的验证来源。** 审查者使用与产出者不同的模型时，发现问题的概率更高。

**通知与人在环。** 轮次达到上限、出现无法自动判断的冲突、涉及高权限操作时，需要通知使用者。

## pi 的做法

pi-subagents 把并发协作、隔离、预算、验收做成了工具参数与工作流脚本，可以逐项核对。

**并发与顺序。** 工具一次调用可以启动一个子任务，也可以用工作流脚本一次启动多个。

```javascript
const [a, b] = await runs.all([
  { key: "impl", agent: "worker", task: "实现功能" },
  { key: "review", agent: "reviewer", task: "独立审查同一份改动" },
]);
return { impl: a.output, review: b.output };
```

`runs.all` 返回与传入顺序一致的数组，`runs.run` 用于需要等待某一个结果之后再决定下一步的场景。并行组有全局并发上限 `globalConcurrencyLimit`，单个运行内有子任务数量上限 `maxSubagentSpawnsPerRun`。

**写入隔离。** `worktree: true` 让每个子任务在独立的 git 工作树里执行，`baseRef` 指定起点。隔离的前提是源工作区干净，否则分配失败。工作树由统一机制创建与清理，`worktree.cleanup` 只做计划不实际删除。一个工作目录同时只允许一个写入者，这是并行写入不互相覆盖的根本保障。

**预算按层级划拨。** `toolBudget` 有软上限与硬上限，达到硬上限之后按白名单屏蔽读取类工具，迫使子智能体进入收尾；`usageBudget` 限制 Token 与金额；`timeoutMs` 限制单次运行时长；`checkpointBeforeDeadlineMs` 让运行在截止前请求子智能体做检查点并停止。额度从父任务向子任务划拨，避免嵌套多层之后总额度被放大。

**验收与证据。** `acceptance` 参数决定证据策略，`gate` 参数在子智能体结束之后执行一条命令，通过标准输出返回结构化结果。验收策略与门禁命令的存在让「子智能体说自己做完了」不再等同于「做完了」。

**独立审查的两种内置角色。** `reviewer` 负责对照任务与计划检查实现、测试、边界情况与简洁性；`evidence-auditor` 负责对重要结论做独立证据审查。`oracle` 是行动前的第二意见，只提出建议不改文件。这三个角色的共同点是上下文独立：不共享产出方的推理过程，因此判断不受其结论影响。

**轮次与返工的控制。** 工作流脚本负责控制返工轮次；`steer` 在运行中对子智能体追加要求而不重启；`resume` 以同一会话继续追问或提出质疑，且存储了原本的 agent、模型与工具约定，因此追问不需要重新交代背景。

**异步与通知。** 默认异步执行。异步运行完成时会主动唤醒发起会话，发起方不需要轮询。需要在本轮拿到结果时用 `async: false` 阻塞父会话。查看进度用 `status` 与 `debug.run`，读取 `status.json`、`events.jsonl` 与日志。

**连续失败的处理规则。** 文档明确规定：工作流、子进程启动、提示词运行时、扩展加载、子工具链的失败属于流程基础设施故障，应当停止并报告确切的失败与运行标识；改用其他执行模式重试会掩盖真实故障。这一条把「重试」与「换一条路径」区分开，避免在未知状态下继续产生副作用。

## 常见错误

第一个错误是没有轮次上限。往返次数不受控制，成本失控。

第二个错误是审查意见写成段落。产出方遗漏部分意见，问题反复出现。

第三个错误是两个子任务同时写入同一工作目录。修改互相覆盖。

第四个错误是子任务各自使用独立额度。嵌套之后总消耗远超预期。

第五个错误是把「子智能体报告的完成」当作完成。没有验收与门禁时，报告与实际状态之间没有约束关系。

第六个错误是在基础设施故障时改用另一种执行模式继续。未知状态下继续执行会放大副作用。

1. 你的协作流程最大轮次是多少？
2. 并行子任务的写入是如何隔离的？
3. 子任务的额度从父任务划拨吗？
4. 子智能体报告完成之后，有没有独立的验收步骤？
