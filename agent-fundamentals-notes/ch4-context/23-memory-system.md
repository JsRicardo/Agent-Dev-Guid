# 23 · Agent 记忆系统

> 章节：第四章 Context Engineering

## 生产中会遇到的问题

会话结束之后，Agent 对之前发生过的事情没有任何印象。使用者需要重复说明习惯、重复提供背景、重复纠正同一个错误。短期会话记忆解决的是当前任务内的连续性，长期记忆解决的是跨会话的连续性。

## 底层机制

记忆按内容类型划分：

| 类型 | 内容 | 变化频率 |
|------|------|----------|
| 事实 | 项目结构、接口约定、环境信息 | 低 |
| 习惯 | 使用者习惯、输出格式要求 | 低 |
| 决策 | 选型结论与理由 | 低 |
| 经验 | 踩过的错误与处理方式 | 中 |
| 状态 | 当前任务进展 | 高 |

按保存形式划分为两派：

**文件派。** 记忆以可读文本保存，由模型直接维护。优点是内容透明、可以手工修改、可以纳入版本管理、不依赖额外服务。缺点是检索能力有限。

**数据库派。** 记忆保存在结构化存储或向量库中，由程序维护写入与检索。优点是检索能力强、支持语义查询、可以按元数据过滤。缺点是内容不透明、写入质量依赖抽取逻辑。

两种方式的差异集中在写入质量与检索能力上。可行的结构是以文件作为权威来源，以索引作为检索入口。

## 实现要点

**分层。** 会话内记忆与跨会话记忆分开。把两者混在一起会让短期内容污染长期记忆。

**作用范围标注。** 每条记忆标注适用范围：全局、某个仓库或项目、某个业务主题。检索时按当前上下文过滤。

**生命周期状态。** 每条记忆有状态：草稿、已验证、已标准化、已废弃、已归档。状态决定是否参与检索。

**写入触发。** 使用者明确要求记录时立即写入。任务结束时写入结论与决策。自动抽取限制在明确的信息类型上。

**检索入口。** 检索时先用标题与说明匹配，命中之后读取完整条目。

## pi 的做法

pi 的记忆系统在结构上属于「文件为权威、索引为入口」的混合方案，而且两层的职责在代码与提示词里都写清楚了。

**短期记忆是会话本身。** 会话以 JSONL 文件保存，条目构成一棵树，`id` 与 `parentId` 描述父子关系，当前节点决定活动分支。这意味着短期记忆没有独立的存储：它就是会话文件。进程重启之后从文件恢复，从任意历史节点继续则形成新分支。

**跨会话记忆是文件目录。** `~/.pi/agent/memory/` 下按内容类型分开：

| 文件或目录 | 内容 | 写入时机 |
|------------|------|----------|
| `MEMORY.md` | 长期条目：决策、习惯、可复用的事实 | 使用者明确要求，或确认了某个持久结论 |
| `daily/<日期>.md` | 当天的过程记录与运行中的上下文 | 过程中随时追加 |
| `SCRATCHPAD.md` | 待处理事项清单 | 发现需要稍后处理的事情时 |
| `recovery/` | 删除操作的恢复记录 | 每一次删除自动生成 |

**检索有三种模式。** 关键词模式适合具体术语、日期、人名与标签；语义模式适合换一种说法找相关概念；深度模式是混合检索加重排。默认走关键词，因为它在大多数查询上足够且快得多。

**元数据决定参与资格。** 每个条目末尾的作用范围与成熟度两项字段决定它是否进入检索结果。作用范围不匹配当前目标的条目不参与；成熟度为已废弃或已归档的条目不参与。

**删除是可恢复的。** 删除条目的操作会生成一条恢复记录并留下可见的恢复标识，可以在发现删错时还原。这一设计针对的是记忆整理过程中最容易出错的动作：删多了无法挽回。

**删除与覆盖的取舍。** 处理一个已经过时的结论时，工具提供的是「按匹配内容删除」，没有原地编辑。旧结论被移除，恢复记录保留依据，新结论作为新条目写入。这样任何时刻文件里的内容都是自洽的当前状态。

## 常见错误

第一个错误是把所有对话内容都写入记忆。检索被噪音污染，重要内容被稀释。

第二个错误是记忆没有作用范围。在 A 项目里学到的做法被应用到 B 项目，造成错误结论。

第三个错误是没有过时检测。事实变化之后旧记忆仍然被检索出来。

第四个错误是冲突时不处理。同一事实存在多条互相矛盾的记录，答案取决于检索顺序。

第五个错误是删除没有恢复路径。整理过程中误删之后无法挽回。

第六个错误是把会话内记忆直接提升为长期记忆。临时性的内容被永久保存。

## 自检问题

1. 你的记忆分为几层，各自的生命周期是什么？
2. 记忆条目里标注了作用范围与状态吗？
3. 检索默认走哪条路径，什么情况下升级到语义检索？
4. 删除记忆之后可以恢复吗？
