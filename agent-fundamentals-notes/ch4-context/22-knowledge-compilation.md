# 22 · LLM 编译知识库

> 章节：第四章 Context Engineering

## 生产中会遇到的问题

检索式知识库的每次查询都从原始文档开始，模型临时组合信息得出答案。同一个问题被问过十次，十次都重新检索、重新组合，结果之间还存在差异。知识没有积累，查询成本不随时间下降。

## 底层机制

两种处理知识的时机：

| 时机 | 做法 | 特点 |
|------|------|------|
| 读时处理 | 检索原始文档，模型临时组合 | 原始信息完整，结果不稳定，重复消耗 |
| 写时编译 | 模型把信息整理成持久文档 | 结果稳定，可积累，整理成本提前付出 |

写时编译的做法是把检索与理解的结果整理成独立条目，条目之间建立链接，后续查询先读条目，需要细节时再回到原始文档。

这套结构的形态接近个人维基：一个主题一个文件，文件头部有元数据，正文里通过链接指向相关主题，另有一个索引文件列出全部条目。

## 实现要点

**条目结构。**

```markdown
# 主题名称

（正文，说明这个主题的事实与结论）

## 关联

- [[相关主题一]]
- [[相关主题二]]

> scope: repo/某个仓库
> updated: 2026-09-24
> source: 原始文档路径或链接
```

正文写结论，来源写依据，关联写上下文。来源字段是核实的基础。

**写入时机。** 三种触发方式：使用者明确要求记录、任务结束时由程序触发、模型判断有新信息时主动写入。第一种最可靠，第三种最容易产生噪音。

**冲突处理。** 新内容与已有条目矛盾时不能直接覆盖。处理方式是标注冲突并保留双方，或者由使用者判定。

**增量更新。** 新信息与已有条目相关时，更新原条目。判断相关性的方式是按主题名称与链接关系查找。

**索引维护。** 索引用来说明有哪些条目以及各自的用途。索引需要定期重建。

## pi 的做法

本机 `~/.pi/agent/memory/` 目录是一套完整的写时编译知识库，结构可以直接打开核对。

```
~/.pi/agent/memory/
├── MEMORY.md            长期条目，一个主题一块，块之间用 HTML 注释标记时间与标识
├── daily/               按日期分文件的过程记录
├── SCRATCHPAD.md        待办与待处理事项
└── recovery/            删除操作的恢复记录
```

几个可以逐项对照的设计：

**写入时机区分明确。** 长期条目与服务过程记录分属不同目录。使用者说「记住这个」时写入长期条目；日常过程写入当天的日志文件；「待会儿要处理的事」写入待办清单。三种内容有不同的生命周期，因此不放在同一个文件里。

**索引与检索分层。** 除了 `MEMORY.md` 本身，还有一份条目元数据目录，记录每条记忆的主题、作用范围与成熟度。检索时先匹配标题与说明，命中之后才读完整条目。这与「先读索引再读正文」的结构一致。

**标签与链接。** 条目里使用 `#标签` 与 `[[链接]]` 两种记号。标签用于跨主题聚类，链接用于声明主题之间的关系。检索的实现可以同时利用这两种记号，而不只依赖文字匹配。

**元数据块固定在条目末尾。** 每条的结尾是作用范围、成熟度、引用次数、最近生效时间四项。成熟度取值有草稿、已验证、已标准化、已废弃、已归档五种，检索时按取值决定是否参与。这一处对应「条目会变坏」的处理：过时内容不删除，改为标记状态。

**来源字段保留。** 条目里记录引用来源与引用次数，内容正确性可以核实，价值判断有依据。

**写时整理。** 长期条目的价值在于压缩后的事实与结论，细节留在原始文件里。条目数量增长不会导致每次加载成本线性上升，因为加载是按命中的条目规模计算的。

## 常见错误

第一个错误是条目写成原始内容摘抄。整理的价值在于压缩与结论化，摘抄不产生新的信息。

第二个错误是条目之间没有链接。孤立条目无法提供上下文，检索时也只能命中单个条目。

第三个错误是直接覆盖旧条目。旧内容消失之后无法判断改动是否合理。

第四个错误是条目没有来源字段。内容正确性无法核实。

第五个错误是把不同生命周期的内容写在同一个文件里。长期结论与过程记录混在一起，整理时无法区分。

第六个错误是把代码细节写进条目。代码会变化，条目写下之后很快过时。

## 自检问题

1. 你的知识库按主题分条目，还是按时间堆在一个文件里？
2. 条目之间有多少条链接？
3. 新信息与已有条目矛盾时，你的处理方式是什么？
4. 每条内容都能追溯到来源吗？
