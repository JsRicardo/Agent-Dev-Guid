# 15 · System Prompt 工程化与 Context Rot

> 章节：第四章 Context Engineering

## 生产中会遇到的问题

系统提示词随着需求增加不断追加内容，从几十行涨到上千行。模型的行为没有变得更可控，反而开始忽略其中的部分规则，或者对矛盾规则做出不可预测的选择。这种现象与上下文长度有关，也与提示词的组织方式有关。

## 底层机制

**Context Rot。** 上下文长度增加之后模型对内容的利用质量下降，下降速度与长度增长不成比例。到达某个长度之后，中部内容的遵循程度明显降低。

**规则冲突。** 提示词中的两条规则覆盖同一场景但给出不同处理方式时，模型的选择不稳定。规则数量增加之后冲突出现的概率上升。

**抽象词汇的弱约束。** 「保持代码整洁」这类表述没有可执行的判定标准，模型的解释随场景变化。

## 实现要点

系统提示词按功能分节，每一节承担一类职责。

```markdown
## 身份与职责
## 决策规则（按优先级排列）
## 工具使用约定
## 输出格式
## 禁止事项
```

**分节之后每一节保持短句。** 每条规则写成一个可判定的断言。避免使用没有边界的词。

**明确冲突处理。** 规则数量增加之后冲突不可避免，在开头写明优先级来源。

**分离动态内容。** 时间、使用者标识、会话标识、当前任务状态都不应写入系统提示词。这些内容会破坏提示词缓存的匹配。

**规则数量控制。** 每条规则都会占用注意力资源。定期清理从未起作用的规则，合并重复的规则。

## pi 的做法

pi 的系统提示词是一个可以逐段落替换、逐段落补丁更新的结构。

**段落生成。** `buildSystemPromptSections` 的默认实现把身份、工具、规则、文档索引四段拼出来。

- `preamble` 固定写明身份与所在环境，然后列出当前选中工具的一行说明。工具数量影响这一段长度：只有被选中且提供了 `promptSnippet` 的工具才出现在清单里。
- `tools` 段落末尾固定附加一句「除上述工具外，项目还可能提供其他自定义工具」。这句的作用是让模型在缺少工具时先检查可用工具。
- `rules` 段落由 `buildRules` 合成：先加基础规则，再按当前选中的工具逐个追加该工具的 `promptGuidelines`，最后加两条通用规则「回答保持简洁」与「处理文件时明确给出路径」。规则用 `Set` 去重，同一条规则不会重复出现。
- 基础规则本身也随工具集合变化。没有 `grep`、`find`、`ls` 而只有 `bash` 时，会补一条「用 bash 做列目录、搜索、找文件这类操作」。

**段落命名有约束。** `SYSTEM_PROMPT_SECTION_NAME` 要求名字以小写字母开头，只含小写字母、数字、下划线、连字符，并且不允许占用 `preamble` 这个名字。自定义段落名不合规时直接抛出错误，不进入静默降级。

**增量更新。** `diffSystemPromptSections` 比较上一版与当前版，只把变化的段落写进一条系统消息：

```typescript
export function diffSystemPromptSections(previous, current) {
  const patch = {};
  for (const [name, text] of Object.entries(current)) {
    if (previous[name] !== text) patch[name] = text;
  }
  for (const name of Object.keys(previous)) {
    if (current[name] === undefined) patch[name] = null;
  }
  return Object.keys(patch).length > 0 ? patch : undefined;
}
```

`null` 表示删除该段落。技能清单变化时只更新 `skills` 一段，其余段落不动，前缀保持一致，提示词缓存继续命中。这一点直接对应「不要在系统提示词里放动态内容」这条规则：pi 让动态部分可以局部替换，整段提示词不需要重写。

**上下文文件的位置与形式。** 上下文文件渲染进独立的 `project_context` 段落，每个文件包一层 `<project_instructions path="...">` 标签。路径出现在标签上，模型引用出处时有据可依。

**强制替换。** 输入里带 `forceSystemPrompt` 时直接返回这一整段内容，不生成任何段落，也不做段落更新。这是给完全接管提示词的使用方准备的出口。

## 常见错误

第一个错误是把系统提示词当作知识库。项目背景、技术说明、历史沿革全部写进去，真正影响行为的部分被大量无关内容稀释。

第二个错误是在提示词里写时间戳。缓存全部失效，成本成倍上升。

第三个错误是规则之间互相矛盾。例如同时要求「先询问再操作」与「不要打断使用者」。

第四个错误是使用无法判定的表述。「写出高质量代码」没有执行方式，模型只能按训练数据里的普遍做法处理。

第五个错误是每次请求重建整段提示词。即使内容只变了一小部分，整段重写也会让缓存失效。

## 自检问题

1. 你的系统提示词有多少行，其中有多少条规则从未生效？
2. 提示词里存在互相矛盾的规则吗？
3. 提示词里有每次请求都变化的字段吗？
4. 提示词变化时你是整段重写，还是只改变化的部分？
