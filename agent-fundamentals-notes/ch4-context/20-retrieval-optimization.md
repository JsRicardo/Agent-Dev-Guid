# 20 · 检索优化

> 章节：第四章 Context Engineering

## 生产中会遇到的问题

检索返回的前几条结果在语义上与查询高度接近，却没有包含回答问题所需的信息。例如查询「为什么这个接口返回 401」，返回的片段都是在描述 401 的含义，而真正需要的是鉴权流程的实现说明。

语义相似衡量的是文字表达接近程度，任务相关衡量的是能否回答当前问题。两者并不一致。

## 底层机制

造成不一致的原因有几个来源：

- **表达差异。** 使用者用口语提问，文档使用专业术语，向量空间里两者距离较远。
- **粒度差异。** 问题需要的是多条信息组合的结论，文档里没有任何一段单独包含这个结论。
- **视角差异。** 文档描述实现方式，问题问的是设计原因，两者词汇接近但内容不对应。
- **噪音来源。** 同一关键词在多个文档中出现，其中只有一处与当前任务相关。

## 实现要点

**查询改写。** 让模型把使用者的提问改写成适合检索的形式，包括补充术语、分解成多个子查询、生成假设性答案再用于检索。

**元数据过滤。** 按来源、时间、类型缩小范围。这一步的效果通常大于调整相似度阈值。

**重排。** 先取较多候选，再用交叉编码模型或由模型直接打分的方式重新排序。

**上下文化分块。** 在离线阶段给每个片段补充所属文档与章节的说明，并在向量化时把说明一并编码。

**调整分块粒度。** 可行的做法是索引使用小块，返回时扩展到相邻块，让模型看到完整上下文。

**建立评测集合。** 准备一批问题与对应的正确来源，改动检索策略之后跑一遍，观察命中率变化。

## pi 的做法

pi 的检索优化集中在两个方面：让模型能自己收窄范围，以及把检索模式的选择权交给调用方。

**收窄范围的参数。** 按内容检索的工具把范围设成必填或强引导的路径参数，模型可以按目录限定搜索范围。按文件名检索与按目录查看各有一个独立工具，三者覆盖不同的查询意图：知道内容但不知道文件名用内容检索，知道文件名但不知道位置用文件名检索，两者都不知道用目录查看。把三种意图分成三个工具，模型不需要在一个工具里切换模式。

**关键词与语义的分工。** 记忆检索提供三种模式：关键词、语义、深度。关键词模式最快，适合查具体术语、日期、人名、标签；语义模式适合换一种说法来找相关概念；深度模式是混合检索加重排，用在前两者都找不到时。这个分层本身就是一条检索优化策略：先走便宜的精确匹配，只在必要时付更贵的语义开销。

**范围的显式标注。** 记忆条目的元数据里有 `scope` 字段，取值为全局、某个仓库、某个业务域。检索时按当前目标过滤，作用范围不符的条目在进入候选集之前就被排除。这一步对应上面的「元数据过滤」，而且它是检索质量改善中最省力的一环。

**引用次数与时间。** 元数据里还有 `refs` 与 `last_relevant` 两个字段，前者记录被引用次数，后者记录最近一次生效的时间。这两个字段让排序可以同时考虑价值与新鲜度。

**评测的位置。** pi 的检索以文件系统与记忆文件为后端，两者都可以直接打开检查。这带来一个实际好处：判断一次检索是否命中不需要搭建标注集，直接打开被返回的条目看内容即可。代价是无法像向量库那样做批量回归，策略调整的效果只能按个案评估。

## 常见错误

第一个错误是只调整相似度阈值。阈值主要影响结果数量，对结果质量影响有限。

第二个错误是重排阶段候选过少。重排无法挽回召回阶段没有取到的内容。

第三个错误是检索结果不标注相关度与来源。模型无法区分主次，使用者无法核实。

第四个错误是忽略元数据。按来源与时间过滤是成本最低的改善手段。

第五个错误是不同查询意图共用一个工具。模型需要在一个工具里切换模式，参数描述会相互干扰，选择准确率下降。

## 自检问题

1. 你的检索结果里带有来源、相关度、作用范围三项信息吗？
2. 你区分了「知道内容」「知道文件名」「都不知道」三种查询意图吗？
3. 你有一条从便宜到昂贵的检索路径吗？
4. 你用什么方式判断一次检索改动是改善还是退化？
